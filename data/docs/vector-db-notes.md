# 向量数据库选型笔记

## 为什么需要专门的向量库

当文本块数量从几千涨到百万级时，「把向量读进内存做一遍矩阵乘法」就不再可行：内存占用按 N×D×4 字节线性增长，单次查询也要扫全量。向量数据库解决的是**在规模下仍然能快速拿到近似最近邻**的问题，核心手段是索引结构 + 分片 + 过滤。

选型时真正要权衡的是三件事：召回率（能不能找到真正最相似的）、查询延迟、以及运维成本。

## 常见索引结构

**Flat（暴力索引）**：逐个比对，召回率 100%，延迟随数据量线性增长。它是小规模数据的默认选择，也常作为其他索引的精度基线——调任何近似索引时，都应该拿 Flat 的结果做对照。

**IVF（倒排文件索引）**：先用聚类把向量空间划成若干桶，查询时只在最近的几个桶里搜。桶数（nlist）和每次探查的桶数（nprobe）决定精度与速度的平衡：nprobe 越大越准越慢。

**HNSW（分层可导航小世界图）**：构建多层近邻图，查询时从上层入口逐层下降。它不需要训练、支持增量写入，查询复杂度近似对数级，是通用场景下的热门选择。两个关键参数：M（每个节点的连接数，影响图质量与内存）、efSearch（查询期搜索宽度，直接决定召回率与延迟）。

需要控制内存时还可以用量化：PQ（乘积量化）把向量压缩到几十分之一，用精度换内存，适合千万级以上的规模。

## 主流产品怎么选

- **FAISS**：Meta 开源的算法库，不是服务。索引类型最全（Flat / IVF / HNSW / PQ 及其组合），常作为其他系统的底层引擎。适合嵌入在自己的进程里、数据量在单机可承载的场景。
- **Chroma**：嵌入式，pip 装完就能用，自带持久化与元数据过滤，开发体验友好，适合原型与中小规模。
- **Milvus / Qdrant**：服务化部署，带分布式、副本、权限与监控能力，适合生产规模与多团队共用。

## 工程注意点

1. **元数据过滤**：真实业务里检索几乎都带过滤条件（租户、时间、权限），要确认索引是否支持「过滤 + 向量检索」的组合，否则会先过滤再暴力扫。
2. **维度与距离度量**：余弦相似度通常用归一化后的内积实现；改成欧氏距离会让已有索引全部失效。
3. **重建成本**：HNSW 支持增量写入，IVF 需要先训练聚类，数据分布漂移后要重新训练，选型时要考虑重建窗口。
4. **别忘了基线**：任何近似索引上线前，都应该用 Flat 在真实查询集上算一次召回率作为验收线。
