# Prompt 工程笔记

## 基本原则

大模型对提示词的措辞相当敏感，同一件事换个说法，效果可能差一个档次。写提示词的核心不是「堆技巧」，而是**把任务边界说清楚**：要做什么、依据什么、输出成什么样、什么情况下该说不知道。

实践中收益最大的三件事：给出明确的角色与任务、给出足够的上下文与示例、给出可校验的输出格式。

## 常用技巧

**少样本示例（Few-shot）**：在提示里放 2～5 个「输入 → 期望输出」的样例，让模型对齐格式与风格。样例要覆盖边界情况，且顺序会影响结果——把最典型的放在最后往往更有效。

**思维链（Chain-of-Thought）**：要求模型先写出推理过程再给结论，能显著提升多步推理类任务的正确率。代价是输出更长、延迟更高，也更容易在中间步骤跑偏。

**角色设定**：给模型一个身份（例如「资深 DBA」），可以低成本地把输出风格拉到目标领域，但不能指望它凭空获得专业知识。

**输出格式约束**：明确要求 JSON / Markdown 表格等结构化格式，并在提示中给出 schema 样例。对需要程序消费的输出，这一步比调温度重要得多。

**约束与兜底**：显式写出「资料不足时回答『未找到相关信息』」这类兜底指令，能明显降低编造率。

## 调参经验

- **temperature**：抽取、分类、打分这类确定性任务设 0；创作类任务 0.7 左右。
- **上下文顺序**：模型对开头和结尾的内容记得更牢，把关键指令放在两端，长资料放中间。
- **指令冲突**：提示里出现互相矛盾的要求时，模型的行为不可预测，需要先消除冲突再调其他参数。

## 常见坑

1. **把示例当成知识**：Few-shot 只教格式与风格，不能替代检索到的真实资料。
2. **提示词无限膨胀**：堆砌所有能想到的规则反而稀释重点，拆成多个子任务通常更可控。
3. **不做回归**：改提示词一定要在固定样例集上跑一遍，否则「感觉变好了」往往是错觉。
4. **忽略截断**：超长上下文会被静默截断，重要信息应前置。
